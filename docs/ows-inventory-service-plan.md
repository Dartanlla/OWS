# OWSInventoryService implementation plan

Status **Draft for review** · November 20, 2026

## Goal and scope

Build an opt-in OWS service for inventories owned by an OWS character. Picking up one item inserts one item or increments one compatible stack. The request, Redis mutation, journal entry, and PostgreSQL write all carry that item-level change, plus the bookkeeping needed for consistency. A move, split, merge, or swap commits only the rows it affects as one transaction. Inventory size should affect storage and page reads without increasing the work for a one-item mutation.

Support numbered-slot and slotless containers through the same API and data model. Nilux will use slotless containers and filter items in its UI. Design for 100,000 concurrent players and prove that target with a realistic mix of inventory sizes, traffic, and infrastructure failures. The proposed first release covers character-owned containers and transactions within one character. Character-to-character trades, shared guild storage, auction houses, and combat equipment persistence can build on the service after their transaction boundaries are designed.

Use both values in every database relationship, Redis key, authorization decision, and command receipt. A character rename has no effect on inventory. Existing OWS session and character-ownership checks are the pattern for any player-facing read gateway. ## Containers and item records

| Concept | Proposed representation |
| --- | --- |
| Character inventory | Owner key, lifecycle generation, and monotonic inventory revision. |
| Container | Stable ContainerId, owner, template key, mode, and capacity policy. A character can have both modes. |
| Item definition | Tenant-scoped stable definition ID with type, tags, stack rules, and optional display references. Use an OWS-compatible catalog contract so games can publish their own definitions and map legacy Items.ItemID where needed. |
| Owned item or stack | Stable ItemInstanceId, container, definition ID, positive quantity, nullable SlotNumber, item revision, and bounded instance metadata such as condition or remaining uses. A unique item has quantity one. |
| Command receipt | Owner and CommandId, canonical request fingerprint, lifecycle generation, result, and committed revision. Used for retry and recovery. |
| Change history | Bounded retention of committed item deltas, indexed by owner and revision. Reuse the receipt's delta when reading the change feed. |

- **Numbered slots.** Each occupied slot holds one item or stack. Use zero-based slot numbers, validate against capacity, and support targeted placement, merge, move, and explicit swap. Empty slots are inferred from capacity and occupancy. Store optional grid dimensions as presentation metadata.
- **Slotless containers.** Each item belongs to a container and has a null slot. The game can configure a stack-count limit or leave it unset. Stack selection uses definition and stack compatibility, including the instance attributes the game declares relevant. An internal cursor or index has no gameplay position.
- **Database rules.** Store one row per owned item or stack. Enforce ownership with composite foreign keys from container to character and from item to container. Pair a row-level mode/slot check with a foreign key to the container's mode. A deferrable unique constraint on (CustomerGUID, CharacterID, ContainerId, SlotNumber) allows many null slots and enforces one item per numbered slot. Defer that constraint inside a swap transaction. Check bounds, capacity, quantity limits, and stack compatibility when applying the command. Index container paging and the supported filters. [PostgreSQL CREATE TABLE](https://www.postgresql.org/docs/14/sql-createtable.html)
- **Changes.** Preserve instance identity when moving a stack. A split creates a new ID. A merge updates the destination and reduces or removes the source. Return deletions in deltas so consumers can remove the old row. Treat a container mode change as a migration with explicit slot assignment.

## API and authoritative gameplay

Start with a private, versioned HTTP API. Game servers authenticate with a tenant-scoped service identity. Player actions go through the game server, which binds the request to its authenticated character. Verify current gameplay authority for player-driven commands. Integrations with server handoff should pass an inventory-side fencing generation checked in the owner transaction, so a superseded server cannot keep writing. An administrative or system grant uses a separately authorized service action.

| Proposed route | Behavior |
| --- | --- |
| GET /v1/characters/{characterId}/inventory/containers | List container IDs, modes, capacities, and revision. |
| GET /v1/characters/{characterId}/inventory/containers/{containerId}/items | Read a bounded page. Use slot order for numbered containers and an opaque cursor for slotless containers. |
| POST /v1/characters/{characterId}/inventory/commands | Apply a typed grant, remove/consume, move, split, merge, or swap. Validate quantities, ownership, capacity, slot rules, and any expected item revisions. |
| GET /v1/characters/{characterId}/inventory/commands/{commandId} | Resolve pending or timed-out submissions and return the original confirmed result. |
| GET /v1/characters/{characterId}/inventory/changes?afterRevision=… | Read a bounded sequence of committed deltas. If the history window has expired, refresh the relevant container pages. |

Use a stable command ID per gameplay action. A duplicate with the same payload returns its current status or original result, including any generated instance IDs. Reuse with a different payload returns a conflict. Keep durable receipts for the documented retry window, preserve them while commands are pending, and reject expired submissions using a trusted issuance timestamp after receipts are pruned. Long-lived reward sources may need a separately retained claim ID. Return only the affected item rows, removed IDs, changed container summaries, and the resulting revision. A stale move or consume conflicts against expected item revisions, while independent grants can proceed without the client resubmitting the entire inventory.

Use capped cursor pages with a container revision and query scope. Restart the affected listing if the revision changes during coherent paging. A moving client can also patch loaded rows from committed deltas and refresh a page on a gap. Start with indexed definition/type filters and let the UI apply game-specific presentation filters. Searches expected to span unloaded pages should use supported service filters or explicitly load all relevant pages. Avoid scanning a whole inventory in a Redis command.

For a pickup, the game server validates the world drop and reserves it for one claimant before submitting the grant. It reuses the same command ID on timeout or restart and consumes the world drop only after confirmed success. A definitive rejection releases the reservation. An unknown outcome keeps the reservation tied to that command for reconciliation. Use recoverable reservation state when loot survives a server restart. Ownership of the same world drop can be contested by two characters, so per-character inventory idempotency alone cannot arbitrate the claim.

## Redis and periodic PostgreSQL sync

1. **Partition by owner.** Assign a stable logical bucket from the composite owner key. Colocate each bucket's character hashes, slot and paging indexes, receipt data, and Redis Stream using a common Redis Cluster hash tag. Partition by enough buckets to distribute work across primaries and allow parallel worker consumption. Each character's mutation fits in a single hash slot. Use bounded item lookups and indexes, and cap how many rows one command can touch. [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
2. **Apply to the hot state and journal.** A bounded Lua operation checks authorization fences, retries, expected versions, and business rules. It computes the exact upserts and deletes, sets an in-progress marker, appends a versioned journal event, updates only the affected Redis rows and indexes, then clears the marker. Include the owner, command ID, previous and next revision, and concrete after-images or deletion markers. Redis scripts isolate concurrent operations, and an error after a write can leave earlier writes applied. The marker blocks use of a partial projection. If no event was appended, reconcile the marker and retry. If the event survived, replay it idempotently or rebuild under a fence from PostgreSQL plus surviving journal entries. [Redis Lua scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/) · [Redis transaction errors](https://redis.io/docs/latest/develop/using-commands/transactions/)
3. **Flush continuously in bounded batches.** Use Redis Stream consumer groups with ordered processing per bucket and pending-entry recovery. Start with a configurable short flush interval, such as 10–25 ms, or flush sooner when the batch fills. The worker applies affected PostgreSQL rows, records the command receipt and resulting revision, and advances its bucket checkpoint in one database transaction. Check the prior character revision and fence the worker by bucket generation and checkpoint so takeover and retries cannot reorder or double-apply changes. A batch can contain several independent commands. Acknowledge stream entries only after the database commits, and trim only through the verified durable checkpoint and required replay window. Stop an affected bucket on an unexplained gap or invariant violation and surface it for repair. [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)
4. **Confirm after PostgreSQL commit in v1.** Keep cache validation and updates off the synchronous database path and batch the disk work. Hold the HTTP request briefly for a committed receipt, or return 202 and a status URL if still pending. Show confirmed items and quantities to gameplay clients. After committing, the worker advances the Redis confirmed watermark and wakes any waiting requests. The durable receipt resolves the result if that notification is missed. Serve a Redis page when the projection matches the confirmed watermark. Otherwise, briefly wait for the watermark to catch up or use a bounded PostgreSQL page under a rate limit. Enable PostgreSQL synchronous commit and agree on the standby/failover policy before promising confirmed-write recovery across a database failover. Redis AOF and replicas help preserve the pending queue, while Redis failover can still lose a tail. Consider Redis-only confirmation later if the project explicitly accepts a measured loss window or adds a durable journal with the required guarantees. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) · [WAITAOF durability limits](https://redis.io/docs/latest/commands/waitaof/)
5. **Recover and bound memory.** Use dedicated Redis with AOF, replicas, no automatic eviction, and explicit backpressure on queue age, memory, and worker health. Evict complete idle character projections only after the durable checkpoint covers them and no pending work remains. Coalesce cold hydrations per character and publish the loaded state behind a revision/generation check. On Redis failover or restore, quarantine affected buckets, fence old workers and projections, reconcile against PostgreSQL checkpoints and receipts, replay the surviving ordered tail, then reopen. Lost unconfirmed submissions can be retried with the original command ID once reconciliation establishes their status. During a PostgreSQL outage, confirmations stall and bounded admission eventually returns a retryable unavailable response. During a Redis outage, safe committed reads can fall back to PostgreSQL, with mutations paused until recovery.

## Nilux integration

Nilux Edge already takes the durable CharacterId from the redeemed OWS ticket and verifies the tenant, user, and character against private Character Persistence. Use that identity to establish inventory access for the authoritative Region. Use Nilux's session and handoff state to drive inventory authority changes, with the generation enforced by Inventory Service. Keep network calls off the simulation thread and apply committed results on the authority that currently owns the character. The Unreal client receives its own container pages and revisions through the game integration. It renders slotless lists keyed by ItemInstanceId and applies its own display filters. See NiluxEdgeServer/README.md and NiluxStateService/README.md under M:/Git/Nilux.

Start with one slotless bag, an authoritative pickup, a move between two containers, and reconnect recovery. Keep the inventory integration separate from admission's AbilitiesGranted lookup. Nilux Region's CharacterLoadout currently accepts whole runtime replacements, has a 1,024-item validation limit, and travels in a bounded handoff payload. When equipment is integrated, project only the equipped item references and combat-relevant fields, and keep the durable inventory revision distinct from the Region loadout revision. Preserve existing ability and progression state when installing the equipment projection. Test stale updates, unequip/removal, and handoff. See NiluxRegionServer/docs/CHARACTER_LOADOUTS.md and NiluxRegionServer/NiluxRegion/NiluxRegion/CharacterLoadout.h.

## Scale and acceptance

- **Separate concurrency from mutation rate.** Start with 100,000 connected players, an illustrative 0.1 inventory commands per player per second (10,000 commands/s), and bursts at 0.5 (50,000 commands/s). Measure list traffic, reconnect storms, hot characters and tenants, realistic metadata, and 2,000–5,000-stack characters. Use observed Nilux playtest rates to revise the workload.
- **Size the cache from the active working set.** At 100,000 characters × 2,000 stack records × an illustrative 500 bytes per record including index overhead, the primary dataset would be roughly 100 GB if all inventories were resident. Add replicas, journal and receipt retention, fragmentation, and AOF rewrite headroom. Measure actual bytes per stack and index, cache hit rates, PostgreSQL row and WAL throughput, and the time needed to drain a sustained backlog.
- **Measure the full path.** Track p50/p95/p99 acceptance and durably confirmed latency separately, along with sync lag, stream backlog, oldest pending age, hydration rate, conflicts, and failover recovery time. Set latency and recovery thresholds before the scale test. Require steady-state sync throughput above the sustained write rate, bounded backlog during the agreed burst, and recovery within the agreed window.
- **Prove transactional behavior.** In integration tests against real Redis and PostgreSQL, verify that a one-item pickup touches one item row regardless of inventory size. Exercise both modes, cross-mode moves, occupied slots, empty and full containers, swaps under deferred uniqueness, concurrent claims, retries after lost responses, and cross-tenant denials. Crash the worker after SQL commit and before stream acknowledgement, force Redis failover and cache loss, and interrupt PostgreSQL through backlog recovery. Check exact quantities, durable receipt identity, and absence of duplicates or lost confirmed commands within the tested database failover model.

## Implementation and rollout

1. Agree on the catalog contract, durability targets, and Nilux integration scope. Add the service, PostgreSQL migration and clean-install path, opt-in deployment, and contracts for both container modes.
2. Implement item commands, receipts, indexes, and the sync/recovery loop. Exercise a slotted reference integration alongside the slotless contract so both modes ship as supported features.
3. Pilot Nilux pickup, move, paging and reconnect with an isolated tenant. Add delivery and handoff tests before enabling live writes. Run the load, soak, and fault tests before raising concurrency.
4. For an existing game, inventory the deployment's legacy sources, verify how saves and relational rows are represented, and dry-run the tenant import. Preserve instance IDs, quantities, slot numbers, condition, uses, and metadata where present. Resolve ambiguous definitions and slot collisions before cutover. Freeze the old writer, import or reconcile the final changes, and verify record-level parity before switching readers and writers. Once new writes begin, rollback requires a verified reverse export or recovery of the new service.

## Decisions for review

1. **Durability and latency.** Is PostgreSQL-confirmed pickup the v1 success rule? What should the p95 target be for confirmed pickups, and how much failover downtime is acceptable?

A: It is important than inventory items are not lost and are always stored in PostgreSQL eventually.  For things like looting rare items in game, we will use a trick where the items is stored in the player's hidden inventory, even before they loot it so that it is impossible for a player to see a rate item (or any item) and lose it.

2. **Nilux catalog and equipment.** Where should stable definition IDs, stack rules, and filter metadata come from? Is persistent equipment needed for the first playable inventory milestone?

A: We will add equipment support later, but it will just be another container.  Item definitions should live in the transactional inventory postgresql DB.  Filters will be defined at the application level, not in this inventory system.  

3. **Legacy adoption.** Is there a specific whole-inventory payload, live slotted deployment, or legacy plugin workflow that v1 must import or support? The plan assumes new transactional endpoints and an opt-in importer for known formats.

A: Nilux currently has no inventory system so it is starting from scratch with a transactional method.  For other OWS game projects that may be using OWS Character Data to store their inventories it is up to them to make the switch manually.  There is no need for legacy support.  This is a brand new opt-in system.
